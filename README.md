# WAMS

Web-based Academic Monitoring System. Three portals — Admin, Professor, Student —
served by a single Express API backed by a Turso (SQLite cloud) database. The
landing page offers Professor and Student sign-in, with a separate Admin sign-in link.

This is a development/scratch project, not a packaged product. See [Recent
changes](#recent-changes) for what has been done so far.

## Setup

### Prerequisites

- Node.js 20 (pinned to the LTS 20 line; see `render.yaml`).
- npm.
- A Turso database (see [Configuration](#configuration)).

### Install dependencies

From the project root:

```bash
npm install
```

Dependencies are declared in the root `package.json`, so a single `npm install`
installs both the server and app dependencies. (The `server/` folder has its own
`package.json` used for the legacy `npm --prefix server` layout.)

### Run the server

```bash
npm start
```

This runs `node server/index.js`, which connects to Turso, seeds the schema,
seeds a default admin account on first boot, and listens on `PORT` (default 3000).

Open `http://localhost:3000` to reach the portal landing page.

## Configuration

Environment variables:

| Variable             | Default                    | Description |
|----------------------|----------------------------|-------------|
| `PORT`               | `3000`                     | HTTP port the server listens on. Render overrides this to `10000`. |
| `JWT_SECRET`         | `administratorSecretKey`   | Secret used to sign auth tokens. The `JWT_SECRET` in `render.yaml` is generated by Render. |
| `TURSO_DATABASE_URL` | _(required)_               | Turso database URL, e.g. `libsql://your-db-name.turso.io`. |
| `TURSO_AUTH_TOKEN`   | _(required)_               | Turso authentication token. |

Copy `.env.example` to `.env` and fill in the Turso credentials for local
development. The database connection is created in `db.js` with `@libsql/client`;
local SQLite was migrated to Turso cloud, so there is no longer a local
`server/wams.db` file to manage (the old `DB_PATH`-based flow is gone).

### Default admin account

On first boot the server seeds:

| Username | Password  | Invite code |
|----------|-----------|-------------|
| `admin`  | `admin123` | `ADMIN2026` |

The invite code is consumed when a second admin registers.

## Portals

| Portal | Path | Login |
|--------|------|-------|
| Landing | `http://localhost:3000/` | Professor and Student portal selection; Admin sign-in is available as a secondary link |
| Admin | `/WAMS/admin/wams-admin-log-in.html` | Username + password (seeded above) |
| Professor | `/WAMS/professor/wams-professor-log-in.html` | Faculty ID + access code issued by Admin |
| Student | `/WAMS/student/wams-student-log-in.html` | Student number + exam access code |

- **Admin**: manage instructors, students, course sections, feedback, system
  health, and real-time dashboard metrics. The admin's name is shown with an
  "Admin" role label on every admin page; PDF/incident reports are attributed to
  the logged-in professor. Departments are reusable records, so removing all
  instructors from a department does not remove it from the add-instructor
  suggestions.
- **Professor**: build exams (WAMS Quiz or Google Forms), run the live monitor
  with camera/screen/audio feeds, review post-exam logs per student, and export
  PDF incident reports.
- **Student**: take exams in a proctored environment with a calculator and
  sketchpad. Entering an exam requests the camera and microphone in a single
  combined permission prompt.

## Features

### Auth & session handling

- JWT-based sessions (24h expiry) for all three roles.
- Auth guards on all protected pages: navigating directly to a dashboard,
  management, monitoring, or exam page without a valid session redirects to the
  appropriate login page.
- 401 responses from the API clear both `token` and `wamsToken` from storage and
  redirect to login, so expired sessions don't leave pages empty/broken.
- Consistent logout across all pages clears both storage keys.
- The student exam tools require an active student session and redirect to the
  student login otherwise.

### Proctoring

- On-device face detection via `face-api.js` (TinyFaceDetector + FaceLandmark68
  models loaded from `WAMS/student/models`). When the AI models are available,
  detected faces are overlaid with hitboxes (eyes, nose, mouth) and captured to
  the proctoring stream. A YCbCr skin-clustering heuristic is kept as a
  fallback if the model fails to load.
- In-browser common-object detection uses the MediaPipe Tasks Vision Object
  Detector with EfficientDet-Lite0 to mark recognized objects (including
  possible phones) in periodic camera stills. A rough head-turn cue is
  estimated from face landmarks; this is not eye-gaze tracking. AI flags are
  imperfect review cues, not proof of misconduct. The
  [MediaPipe runtime](https://github.com/google-ai-edge/mediapipe) is
  Apache-2.0 licensed; verify the separately hosted
  [EfficientDet-Lite0 model weights](https://storage.googleapis.com/mediapipe-tasks/object_detector/efficientdet_lite0_uint8.tflite)
  terms before redistributing those weights.
- Approximate sustained audio-activity cues measured from microphone RMS
  amplitude in dBFS. This signal-level heuristic does not identify speakers
  and may mistake speech, noise, or other sounds for activity; only stored
  audio clips can be played in Monitoring Logs (no synthetic audio fallback).
- Background screen capture: students are prompted for screen sharing on exam
  entry; periodic high-resolution snapshots are captured to the stream.
- Tab-switch / visibility-change tracking with timestamps.
- Students must acknowledge a pre-exam privacy notice referencing the Data
  Privacy Act of 2012 (Republic Act No. 10173). Late entrants receive only the
  time remaining after the scheduled start or the instructor's manual start.

### Exam lifecycle

- A server-side lifecycle task checks scheduled exams every five seconds.
  Scheduled exams become `live` at their start time and become `ended` when the
  configured time limit expires. A manual instructor start anchors the timer to
  the start action. Students need the exam access code and cannot enter before
  an exam is live; a correct code receives a clear not-started or ended message.
  Student exam pages also stop when the server reports that the exam has ended,
  and answer submissions and exam activity writes are rejected outside the live
  period.
- Sections are de-duplicated at creation time and a unique index
  (`idx_sections_name_course`) exists on `sections(name, course)`. Student login
  additionally falls back to matching by section name, which protects against
  duplicate/orphaned section rows.

### System telemetry

The dashboard endpoint (`/api/dashboard`) reports live system health:
- CPU usage via `process.cpuUsage()` deltas (sampled per request).
- Memory (free/total, as a percentage).
- Database size (estimated from record counts — the DB is now cloud-hosted, so
  file-size probing is not used).
- Network load (derived from live exams and flagged sessions).
- Storage (process heap usage).

## Architecture notes

- Single Express server (`server/index.js`), plain HTML/CSS/JS on the client —
  no build step, no framework.
- Relative asset paths: the app runs from the project root and is mounted under
  `/WAMS/...`, so pages work both at the domain root and under a sub-path.
- All third-party libraries used by the client (Chart.js, jsPDF) are vendored
  under `WAMS/vendor/`, so the client works offline. `face-api.min.js` is
  vendored under `WAMS/student/`. The MediaPipe runtime and object-detection
  model are fetched from jsDelivr and Google Storage at runtime; camera frames
  are processed locally and are not sent to either asset host.
- The server blocks direct access to sensitive files: `.db`, `server/`,
  `node_modules/`, `.git/`, `.env`, and `package*.json` are all served as 404s.
- SQLite was replaced by Turso (`@libsql/client`). The `@libsql/client`
  dependency is declared in both the root and `server/` package files.

## Deployment

`render.yaml` declares a Render web service:

```yaml
services:
  - type: web
    name: wams
    env: node
    plan: free
    buildCommand: npm install
    startCommand: npm start
    ...
```

The service runs the Express app from the repository root. Its `/` route serves
the root `index.html` as the deployed portal landing page.

- Plan: free tier.
- `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` are synced from Render's secret
  store (marked `sync: false` so they aren't exposed in the public repo).
- A persistent disk is attached so uploaded data isn't lost when the instance
  sleeps — though the primary state now lives in Turso.

For local development there is no persistent disk; the database lives entirely
in Turso, and the only local state is the `.env` file of credentials.
